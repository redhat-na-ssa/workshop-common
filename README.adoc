= Workshop common

The site look and build workflows shared by the OpenShift workshops:

* `openshift-101-workshop` (OpenShift 101)
* `openshift-102-workshop` (OpenShift 102)
* `ocp-cloud-workshop` (OpenShift on AWS and Azure)

The workshops and this repo live under the same GitHub owner; `<owner>` below stands for it.
Moving them to another owner means changing `<owner>` in each workshop's playbooks and workflows.

Change something here once and every workshop picks it up on its next site build.
`workshops.txt` lists them, and <<adding-a-workshop>> starts a new one.

== What's shared

[cols="1,2"]
|===
|Path |What it is

|`ui/`
|Files laid over the https://github.com/rhpds/rhdp_showroom_theme[Red Hat Showroom theme]: extra CSS (`css/site-extra.css`), tabs (`css/tabs.css`, `js/vendor/tabs.js`), the copy button on every code block and the build stamp (`partials/footer.hbs`, `partials/build-info.hbs`), and the favicon.

|`scripts/build-ui-bundle.sh`
|Downloads the theme, lays `ui/` over it and zips the result. The theme version is set at the top of the script.

|`.github/workflows/pages.yml`
|Reusable workflow that builds a workshop site with Antora, stamps the footer with the release, commit and build time, and deploys it to the workshop's GitHub Pages.

|`.github/workflows/pdf-release.yml`
|Reusable workflow that builds a workshop PDF and publishes it as a release.

|`.github/workflows/pdf-test.yml`
|Reusable workflow that builds a workshop PDF on a pull request, without publishing it.

|`.github/workflows/content-check.yml`
|Reusable workflow that checks a pull request: the formatting conventions on the lines it changes, a site build with no Antora warnings, and every link inside the built site. See <<checks>>.

|`scripts/preview.sh`
|Builds a workshop site the way the Pages workflow does and serves it locally, optionally rebuilding on every change and with this checkout's `ui/`. See <<previewing-a-workshop>>.

|`scripts/check-content.py`, `scripts/check-links.py`
|The checks it runs. Both also run locally.

|`template/`, `scripts/new-workshop.sh`
|The starting point for a new workshop, and the script that copies it into a new repo. See <<adding-a-workshop>>.

|`workshops.txt`
|The workshops that use this repo. Their sites are rebuilt after every merge here.

|`.github/workflows/template-test.yml`
|Starts a workshop from the template on every pull request and builds its site and PDF, so the template keeps working.

|`.github/workflows/publish.yml`
|This repo's own workflow: on every change to `main` it rebuilds `ui-bundle.zip` and replaces it on the `ui-bundle` release.
|===

== Versions in the footer

Each site's footer shows two versions: the workshop's own release and commit, and the version of this repo its look came from, for example:

----
Release v1.0.0 + 2 commits · Commit 69f6dbc · Shared setup v1.0.0 + 1 commit · Built 2026-10-16 14:00 UTC
----

The workshop's values come from the Pages workflow; the shared one is written into the bundle by `scripts/build-ui-bundle.sh` from this repo's latest `v*` tag and commit, and links to that commit.
A bundle built from uncommitted changes says so.
To give the shared setup a release number, create a `v*` release here, then run *Publish UI bundle* and the workshop Pages workflows.

Each workshop keeps its content, its Antora playbooks, its `Gemfile` and anything only it needs, such as OpenShift 102's offline bundle release and the cloud workshop's sample app image.

== How the workshops use it

Every workshop playbook loads the bundle from the `ui-bundle` release:

[source,yaml]
----
ui:
  bundle:
    url: https://github.com/<owner>/workshop-common/releases/download/ui-bundle/ui-bundle.zip
    snapshot: true
----

`snapshot: true` makes Antora download it again on every build, so local, container and Showroom builds get the current look too.

Each workshop's workflows call the reusable ones on `main`:

[source,yaml]
----
jobs:
  pages:
    uses: <owner>/workshop-common/.github/workflows/pages.yml@main
----

To hold a workshop back on an older version, replace `@main` with a tag or commit of this repo, and point its playbooks at a bundle saved from that version.

== Making a change

. Edit the files under `ui/`, or a workflow.
. Try a UI change on a workshop before merging. From a workshop checkout, preview it with the bundle built from your copy of this repo:
+
[source,bash]
----
../workshop-common/scripts/preview.sh --local-ui
----
. Open a pull request. The *Publish UI bundle* workflow builds the bundle and keeps it as a run artifact.
. Merge it. The workflow replaces the bundle on the `ui-bundle` release.
. Rebuild the sites, unless the `WORKSHOP_DISPATCH_TOKEN` secret below is set:
+
[source,bash]
----
for r in $(sed -e "s/#.*//" workshops.txt); do
  gh workflow run gh-pages.yml \
    --repo "<owner>/$r"
done
----

=== Rebuilding the sites automatically

Add a repository secret named `WORKSHOP_DISPATCH_TOKEN` holding a fine-grained token with *Actions: Read and write* on the workshop repos.
*Publish UI bundle* then runs each workshop's Pages workflow after every merge.
It rebuilds the repos in `workshops.txt`; a repository variable `WORKSHOP_REPOS`, holding names separated by spaces, replaces that list.

[#previewing-a-workshop]
== Previewing a workshop

Every workshop previews the same way.
With this repo checked out next to the workshop, run this from the workshop's folder:

[source,bash]
----
../workshop-common/scripts/preview.sh --watch
----

It builds the site with the same Antora version and extensions as the Pages workflow, serves it on http://localhost:8080/ and rebuilds it when you save a change.
`--local-ui` uses this checkout's `ui/` instead of the published bundle, `--no-serve` only builds, and a playbook name builds that playbook instead of `default-site.yml`.
It needs Node.js and Python 3.

[#adding-a-workshop]
== Adding a workshop

A new workshop starts from `template/`, which has the playbooks, the workflows, an introduction, a setup requirements page and a sample module page that shows the formatting conventions.
The steps use the GitHub CLI, signed in to an account that can create repos under the owner of this repo.

. From this repo's checkout, create the workshop next to it.
The folder name becomes the repo name, and the owner is this repo's owner:
+
[source,bash]
----
scripts/new-workshop.sh ../openshift-201-workshop "OpenShift 201"
----

. Create the repo on GitHub and push `main`:
+
[source,bash]
----
gh repo create <owner>/openshift-201-workshop \
  --public \
  --source ../openshift-201-workshop \
  --push
----

. Turn on GitHub Pages with GitHub Actions as the source:
+
[source,bash]
----
gh api repos/<owner>/openshift-201-workshop/pages \
  --method POST \
  --field build_type=workflow
----

. Publish the site.
The push in step 2 ran before Pages was on, so run the Pages workflow again:
+
[source,bash]
----
gh workflow run gh-pages.yml \
  --repo <owner>/openshift-201-workshop
----
+
The site appears at `https://<owner>.github.io/openshift-201-workshop/`.

. Optional: serve it at a custom domain.
Point a DNS CNAME record for the name at `<owner>.github.io`, set the name on the repo, then run the Pages workflow again as in step 4:
+
[source,bash]
----
gh api repos/<owner>/openshift-201-workshop/pages \
  --method PUT \
  --field cname=openshift-201.example.com
----

. Register the workshop here, in one pull request: add its name to `workshops.txt` and to the list at the top of this README.
If the `WORKSHOP_DISPATCH_TOKEN` secret is set, also add the repo to that token's repository access in your GitHub token settings, or its site won't rebuild after a merge here.

. Write the workshop.
Replace the sample pages under `content/modules/ROOT/pages`, list them in `nav.adoc`, and fill in `setup-requirements.adoc`: every workshop lists the cluster components, Operators, command-line tools, roles and access it needs.
Work in pull requests, so *Check content* and *Test PDF Build* run on each one.

. Publish the first release and its PDF:
+
[source,bash]
----
gh workflow run build-and-release-pdf.yml \
  --repo <owner>/openshift-201-workshop \
  --field tag_name=v1.0.0
----

To change what every new workshop starts with, edit `template/`.
Its placeholders are `@@TITLE@@`, `@@REPO@@` and `@@OWNER@@`, and *Test the workshop template* builds it on every pull request.
Changing the template doesn't change workshops that already exist.

[#checks]
== Pull request checks

Every workshop pull request runs *Check content*, which fails when:

* A line the pull request adds to a code block is longer than 76 characters, which the PDF cuts off.
Break a long command with a backslash, one flag per indented line.
* A line the pull request adds puts a runnable command in a sentence.
A command counts as runnable when it pipes or chains, has five or more words, or follows _run_, _enter_, _type_, _execute_ or _paste_.
Put it in its own code block.
Commands in tables and plain mentions, such as "`oc login` signs you in", are fine.
* Antora warns while building the site, for example about an xref to a page that doesn't exist.
* A link or image inside the built site points to a page, file or section that doesn't exist.

Only the lines a pull request changes are held to the conventions, so older pages don't have to be cleaned up first.
To allow an exception, put a comment line right above the code block or the sentence:

....
// check: long-lines
[source,yaml]
----
....

....
// check: inline-ok
Run `oc get pods | grep Running` only if you want the short list.
....

To run the checks before pushing, from a workshop checkout:

[source,bash]
----
../workshop-common/scripts/check-content.py --base origin/main
----

[source,bash]
----
antora generate default-site.yml \
  --to-dir /tmp/site \
  --log-failure-level warn
----

[source,bash]
----
../workshop-common/scripts/check-links.py /tmp/site
----

Without `--base`, `check-content.py` checks every line, which lists the older problems too.

== Reusable workflow inputs

`pages.yml`:: `playbook` (default `default-site.yml`), `output-dir` (`www`), `extra-npm-packages` (installed next to Antora 3.1 and `@asciidoctor/tabs`), `helm-version` (installs Helm when set), `post-build` (a command run after the site is built). The caller grants `contents: read`, `pages: write` and `id-token: write`.
`pdf-release.yml`:: `tag-name`, `pdf-name` and `pdf-title` (required), `playbook` (`default-pdf.yml`), `output-dir` (`www`). The caller grants `contents: write`.
`content-check.yml`:: `playbook` (`default-site.yml`), `extra-npm-packages`, `common-ref` (the branch, tag or commit of this repo to take the check scripts from, `main`). The caller grants `contents: read`.
`pdf-test.yml`:: `playbook` (`default-pdf.yml`), `output-dir` (`www`), `single-pdf` (fail unless exactly one PDF is built). The caller grants `contents: read`.
