= Workshop common

The site look and build workflows shared by the OpenShift workshops:

* `openshift-101-workshop` (OpenShift 101)
* `openshift-102-workshop` (OpenShift 102)
* `openshift-103-workshop` (OpenShift 103: ROSA and ARO)

All of them share one layout (see <<layout>>) and release the same way (see <<releases>>).

The workshops and this repo live under the same GitHub owner; `<owner>` below stands for it.
Moving them to another owner means changing `<owner>` in each workshop's playbooks and workflows.

Change something here once and every workshop picks it up on its next site build.
`workshops.txt` lists them, and <<adding-a-workshop>> starts a new one.

== What's shared

[cols="1,2"]
|===
|Path |What it is

|`ui/`
|Files laid over the https://github.com/rhpds/rhdp_showroom_theme[Red Hat Showroom theme]: extra CSS (`css/site-extra.css`), tabs (`css/tabs.css`, `js/vendor/tabs.js`), the Red Hat logo in the header (`partials/header-content.hbs`), the copy button on every code block and the build stamp (`partials/footer.hbs`, `partials/build-info.hbs`), link colors and the favicon.

|`pdf/`
|The look of every workshop PDF: the theme (`workshop-theme.yml`) with its Red Hat fonts and title page, and `workshop-pdf.rb`, which each workshop's `antora-assembler.yml` loads. See <<pdf-look>>.

|`scripts/build-ui-bundle.sh`
|Downloads the theme, lays `ui/` over it and zips the result. The theme version is set at the top of the script.

|`.github/workflows/pages.yml`
|Reusable workflow that builds a workshop site with Antora, stamps the footer with the release, commit and build time, and deploys it to the workshop's GitHub Pages.

|`.github/workflows/release.yml`
|Reusable workflow that publishes a workshop release with everything needed to run it disconnected. See <<releases>>.

|`offline/`
|What a release builds from: the runtime image (`Dockerfile.runtime`), the tools image (`Dockerfile.tools`, with the `docker` shim and shell banner), the Helm chart (`chart/`), and the `DISCONNECTED.md`, `TOOLS.md` and `tools-deployment.yaml` that ship in the offline bundle.

|`scripts/package-offline.sh`, `scripts/verify-tools-image.sh`
|Render and package a workshop's chart and offline files, and check its tools image. Both also run locally.

|`.github/workflows/pdf-test.yml`
|Reusable workflow that builds a workshop PDF on a pull request, without publishing it.

|`.github/workflows/content-check.yml`
|Reusable workflow that checks a pull request: the formatting conventions on the lines it changes, a site build with no Antora warnings, and every link inside the built site. See <<checks>>.

|`scripts/preview.sh`
|Builds a workshop site the way the Pages workflow does and serves it locally, optionally rebuilding on every change, with this checkout's `ui/`, or for one workshop alone. See <<previewing-a-workshop>>.

|`scripts/check-content.py`, `scripts/check-links.py`
|The checks it runs. Both also run locally.

|`template/`, `scripts/new-workshop.sh`
|The starting point for a new workshop repo, and the script that copies it into a new repo. See <<adding-a-workshop>>.

|`template-workshop/`, `scripts/add-workshop.py`
|The starting point for one more workshop inside a repo, and the script that adds it. See <<layout>>.

|`scripts/standalone-playbook.py`
|Writes a playbook that builds one workshop of a repo on its own, for `preview.sh --workshop` and the pull request checks.

|`workshops.txt`
|The workshops that use this repo. Their sites are rebuilt after every merge here.

|`.github/workflows/template-test.yml`
|Starts a workshop from the template on every pull request and builds its site and PDF, so the template keeps working.

|`.github/workflows/publish.yml`
|This repo's own workflow: on every change to `main` it rebuilds `ui-bundle.zip` and replaces it on the `ui-bundle` release.
|===

== Versions in the footer

Each site's footer shows two versions: the workshop's own release and commit, and the version of this repo its look came from, for example:

----
Release v1.0.0 + 2 commits · Commit 69f6dbc · Shared setup v1.0.0 + 1 commit · Built 2026-10-16 14:00 UTC
----

The workshop's values come from the Pages workflow; the shared one is written into the bundle by `scripts/build-ui-bundle.sh` from this repo's latest `v*` tag and commit, and links to that commit.
A bundle built from uncommitted changes says so.
To give the shared setup a release number, create a `v*` release here, then run *Publish UI bundle* and the workshop Pages workflows.

Each workshop keeps its content, its Antora playbooks, its `Gemfile`, its own tools (`tools/install.sh`) and anything only it needs, such as OpenShift 103's sample app image.

[#layout]
== Workshop layout

Every workshop repo is one site made of several workshops, each of which can be built and tested on its own:

[cols="1,2"]
|===
|Path |What it is

|`content/`
|The home part, the same in every repo: *Workshop home* (`index.adoc`: what the site is and where to start), *Workshop instructor* (`instructor.adoc`: what the workshops cover, the environment and requirements, delivery notes) and *Workshop attendee* (`attendee.adoc`: how the workshops work and where to begin).

|`workshops/<name>/`
|One workshop: its own `antora.yml`, and its pages, navigation, images and examples under `modules/<name>/`, including its `setup-requirements.adoc`. Its pages are at `/<name>/` on the site.

|`tools/install.sh`, `tools/extra-tools`
|The command-line tools the workshops need beyond the shared ones, added to the release's tools image.
|===

All the parts are one Antora component (`name: ROOT`, no version), so one navigation spans every workshop.
The playbooks list `content/` last, which makes its `antora.yml` the one the site uses: its title, its navigation list (the home part's, then each workshop's) and its AsciiDoc attributes, which must include every attribute any workshop needs.
A workshop's own `antora.yml` applies only when it is built alone.

To add a workshop to a repo, from the repo's folder:

[source,bash]
----
../workshop-common/scripts/add-workshop.py running-applications "Running Applications"
----

It copies `template-workshop/` to `workshops/running-applications/` and lists the workshop everywhere the site needs it: both playbooks, `content/antora.yml`, the home part's navigation and its three pages.
Each of those has a line that says `add-workshop.py adds workshops above this line`; keep those lines.
Then write its pages and fill in its row on the instructor page and its setup requirements.

Link between pages of one workshop with `xref:page.adoc[]`, to another workshop with `xref:<name>:page.adoc[]`, and to a home page with `xref:ROOT:instructor.adoc[]`.
Every workshop must also build on its own, so keep links out of a workshop into the others, or guard them with an attribute only `content/antora.yml` sets.

== How the workshops use it

Every workshop playbook loads the bundle from the `ui-bundle` release:

[source,yaml]
----
ui:
  bundle:
    url: https://github.com/<owner>/workshop-common/releases/download/ui-bundle/ui-bundle.zip
    snapshot: true
----

`snapshot: true` makes Antora download it again on every build, so local, container and Showroom builds get the current look too.

Each workshop's workflows call the reusable ones on `main`:

[source,yaml]
----
jobs:
  pages:
    uses: <owner>/workshop-common/.github/workflows/pages.yml@main
----

To hold a workshop back on an older version, replace `@main` with a tag or commit of this repo, and point its playbooks at a bundle saved from that version.

== Making a change

. Edit the files under `ui/`, or a workflow.
. Try a UI change on a workshop before merging. From a workshop checkout, preview it with the bundle built from your copy of this repo:
+
[source,bash]
----
../workshop-common/scripts/preview.sh --local-ui
----
. Open a pull request. The *Publish UI bundle* workflow builds the bundle and keeps it as a run artifact.
. Merge it. The workflow replaces the bundle on the `ui-bundle` release.
. Rebuild the sites, unless the `WORKSHOP_DISPATCH_TOKEN` secret below is set:
+
[source,bash]
----
for r in $(sed -e "s/#.*//" workshops.txt); do
  gh workflow run gh-pages.yml \
    --repo "<owner>/$r"
done
----

=== Rebuilding the sites automatically

Add a repository secret named `WORKSHOP_DISPATCH_TOKEN` holding a fine-grained token with *Actions: Read and write* on the workshop repos.
*Publish UI bundle* then runs each workshop's Pages workflow after every merge.
It rebuilds the repos in `workshops.txt`; a repository variable `WORKSHOP_REPOS`, holding names separated by spaces, replaces that list.

[#previewing-a-workshop]
== Previewing a workshop

Every workshop previews the same way.
With this repo checked out next to the workshop, run this from the workshop's folder:

[source,bash]
----
../workshop-common/scripts/preview.sh --watch
----

It builds the site with the same Antora version and extensions as the Pages workflow, serves it on http://localhost:8080/ and rebuilds it when you save a change.
`--local-ui` uses this checkout's `ui/` instead of the published bundle, `--no-serve` only builds, and a playbook name builds that playbook instead of `default-site.yml`.
`--workshop <name>` builds only `workshops/<name>`, the way it will look on its own, to test it before it joins the site:

[source,bash]
----
../workshop-common/scripts/preview.sh --watch --workshop running-applications
----

It needs Node.js and Python 3.

[#pdf-look]
== PDF look

Every workshop PDF gets its look from `pdf/`: a title page, a table of contents, page headers with the workshop and chapter, the release in the footer, the Red Hat Display, Text and Mono fonts, and tan code blocks like the copyable ones on the sites.
`pdf/workshop-pdf.rb` also prints each `[tabs]` tab, such as ROSA (AWS) and ARO (Azure), as its own labeled panel, prints collapsible blocks as tinted panels, and moves a short code block or note to the next page whole instead of splitting it.

Each workshop's `antora-assembler.yml` loads it from a checkout of this repo next to the workshop:

[source,yaml]
----
build:
  command: bundle exec asciidoctor-pdf -r ../workshop-common/pdf/workshop-pdf.rb
----

The PDF workflows check this repo out there.
To build a PDF locally, clone this repo next to the workshop, then from the workshop checkout:

[source,bash]
----
bundle install
----

[source,bash]
----
antora generate default-pdf.yml \
  --attribute revnumber=v1.0.0
----

`revnumber` is the version on the title page and in the footers; the release workflow sets it to the release tag.
To change the look of every PDF, edit `pdf/workshop-theme.yml` (the https://docs.asciidoctor.org/pdf-converter/latest/theme/[Asciidoctor PDF theme keys]); the fonts are under the SIL Open Font License in `pdf/fonts/OFL.txt`.

[#adding-a-workshop]
== Adding a workshop

A new workshop repo starts from `template/`, which has the playbooks, the workflows and the home part, and one workshop from `template-workshop/`, with a setup requirements page and a sample module page that shows the formatting conventions.
The steps use the GitHub CLI, signed in to an account that can create repos under the owner of this repo.

. From this repo's checkout, create the workshop next to it.
The folder name becomes the repo name, and the owner is this repo's owner:
+
[source,bash]
----
scripts/new-workshop.sh ../openshift-201-workshop "OpenShift 201 Workshop"
----
+
The first workshop inside it is `workshops/first-steps`; name it yourself with two more arguments, such as `operators "Operators"`.

. Create the repo on GitHub and push `main`:
+
[source,bash]
----
gh repo create <owner>/openshift-201-workshop \
  --public \
  --source ../openshift-201-workshop \
  --push
----

. Turn on GitHub Pages with GitHub Actions as the source:
+
[source,bash]
----
gh api repos/<owner>/openshift-201-workshop/pages \
  --method POST \
  --field build_type=workflow
----

. Publish the site.
The push in step 2 ran before Pages was on, so run the Pages workflow again:
+
[source,bash]
----
gh workflow run gh-pages.yml \
  --repo <owner>/openshift-201-workshop
----
+
The site appears at `https://<owner>.github.io/openshift-201-workshop/`.

. Optional: serve it at a custom domain.
Point a DNS CNAME record for the name at `<owner>.github.io`, set the name on the repo, then run the Pages workflow again as in step 4:
+
[source,bash]
----
gh api repos/<owner>/openshift-201-workshop/pages \
  --method PUT \
  --field cname=openshift-201.example.com
----

. Register the workshop here, in one pull request: add its name to `workshops.txt` and to the list at the top of this README.
If the `WORKSHOP_DISPATCH_TOKEN` secret is set, also add the repo to that token's repository access in your GitHub token settings, or its site won't rebuild after a merge here.

. Write the workshop.
Fill in the home part's three pages under `content/modules/ROOT/pages`, replace the sample pages under `workshops/first-steps/modules/first-steps/pages`, list them in that workshop's `nav.adoc`, and fill in its `setup-requirements.adoc`: every workshop lists the cluster components, Operators, command-line tools, roles and access it needs.
Add more workshops with `add-workshop.py` (see <<layout>>), and the tools they need to `tools/install.sh`.
Work in pull requests, so *Check content* and *Test PDF Build* run on each one.

. Publish the first release (see <<releases>>), then make its two images public under the owner's *Packages*:
+
[source,bash]
----
gh workflow run release.yml \
  --repo <owner>/openshift-201-workshop \
  --field tag_name=v1.0.0
----

To change what every new workshop starts with, edit `template/`.
Its placeholders are `@@TITLE@@`, `@@REPO@@` and `@@OWNER@@` (and `@@NAME@@` and `@@WTITLE@@` in `template-workshop/`), and *Test the workshop template* builds it, its PDF and its images on every pull request.
Changing the template doesn't change workshops that already exist.

[#checks]
== Pull request checks

Every workshop pull request runs *Check content*, which fails when:

* A line the pull request adds to a code block is longer than 76 characters, which the PDF cuts off.
Break a long command with a backslash, one flag per indented line.
* A line the pull request adds puts a runnable command in a sentence.
A command counts as runnable when it pipes or chains, has five or more words, or follows _run_, _enter_, _type_, _execute_ or _paste_.
Put it in its own code block.
Commands in tables and plain mentions, such as "`oc login` signs you in", are fine.
* Antora warns while building the site, for example about an xref to a page that doesn't exist.
* A link or image inside the built site points to a page, file or section that doesn't exist.
* A workshop under `workshops/` doesn't build on its own without warnings.

Only the lines a pull request changes are held to the conventions, so older pages don't have to be cleaned up first.
To allow an exception, put a comment line right above the code block or the sentence:

....
// check: long-lines
[source,yaml]
----
....

....
// check: inline-ok
Run `oc get pods | grep Running` only if you want the short list.
....

To run the checks before pushing, from a workshop checkout:

[source,bash]
----
../workshop-common/scripts/check-content.py --base origin/main
----

[source,bash]
----
antora generate default-site.yml \
  --to-dir /tmp/site \
  --log-failure-level warn
----

[source,bash]
----
../workshop-common/scripts/check-links.py /tmp/site
----

Without `--base`, `check-content.py` checks every line, which lists the older problems too.

[#releases]
== Releases

Every workshop releases the same way, so it can run in a disconnected cluster from what the release holds.
Run the workshop's *Release* workflow with the next version, or push a tag of that name:

[source,bash]
----
gh workflow run release.yml \
  --repo <owner>/<workshop> \
  --field tag_name=v1.1.0
----

It calls `.github/workflows/release.yml` here, which publishes:

[cols="1,2"]
|===
|What |Name

|The PDF of the whole site
|`<workshop>-<tag>.pdf`

|The site, built to serve at the root of a container, on port 8080
|`ghcr.io/<owner>/<workshop>:<tag>` (and `latest`)

|The tools image: the shared tools (`oc`, `kubectl`, `helm`, `jq`, `yq`, `git`, `curl`, `wget`, `skopeo`, a `docker` shim), the workshop's `tools/install.sh` and the Helm chart in `~/chart`
|`ghcr.io/<owner>/<workshop>-tools:<tag>` (and `latest`)

|The Helm chart, which runs the site and a tools pod; also served from the site at `/helm/`
|`<workshop>-<version>.tgz`

|The offline bundle: the site, the chart, the PDF, `DISCONNECTED.md`, `TOOLS.md`, `tools-deployment.yaml` and the list of images to mirror
|`<workshop>-offline-<tag>.tar.gz`

|SBOMs of both images
|`<workshop>-<tag>.sbom.cdx.json`, `<workshop>-tools-<tag>.sbom.cdx.json`
|===

The first time a workshop releases, make both images public under the owner's *Packages*, so clusters can pull them without credentials.
Pages builds also serve the chart at `/helm/`.

To check a workshop's tools image locally, with Docker or Podman, from the workshop's folder:

[source,bash]
----
../workshop-common/scripts/package-offline.sh --out /tmp/offline
----

[source,bash]
----
cp -R ../workshop-common .workshop-common
----

[source,bash]
----
docker build \
  --file .workshop-common/offline/Dockerfile.tools \
  --tag tools:test \
  .
----

[source,bash]
----
../workshop-common/scripts/verify-tools-image.sh tools:test
----

Delete `.workshop-common` afterwards; the release workflow checks this repo out there itself.

== Reusable workflow inputs

`pages.yml`:: `playbook` (default `default-site.yml`), `output-dir` (`www`), `extra-npm-packages` (installed next to Antora 3.1 and `@asciidoctor/tabs`), `helm-chart` (serve the workshop's chart at `/helm/`, `true`), `helm-version` (the Helm version to install), `post-build` (a command run after the site is built), `common-ref` (`main`). The caller grants `contents: read`, `pages: write` and `id-token: write`.
`release.yml`:: `tag-name` and `title` (required), `site-playbook` (`default-site.yml`), `pdf-playbook` (`default-pdf.yml`), `common-ref` (the branch, tag or commit of this repo to take `offline/`, `pdf/` and the scripts from, `main`). The caller grants `contents: write` and `packages: write`.
`content-check.yml`:: `playbook` (`default-site.yml`), `extra-npm-packages`, `common-ref` (the branch, tag or commit of this repo to take the check scripts from, `main`). The caller grants `contents: read`.
`pdf-test.yml`:: `playbook` (`default-pdf.yml`), `output-dir` (`www`), `common-ref` (`main`), `single-pdf` (fail unless exactly one PDF is built). The caller grants `contents: read`.
